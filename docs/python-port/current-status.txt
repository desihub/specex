Written 2026-07-21, condensed to a bottom-line-only snapshot 2026-09-09.

This file answers ONE question -- "where does this project stand right now"

===============================================================================
1. BOTTOM LINE
===============================================================================
Cumulative over 20 independent full-night/expid campaigns (30 cameras each,
two non-overlapping 10-night sets, 2026-08-11/12 and 2026-09-02/05):

  - Correctness vs. C++: mean xrms=0.0120px, mean yrms=0.0129px (range xrms
    0.0112-0.0140px, yrms 0.0111-0.0167px).
  - Timing: with --worker-mode persistent (the fastest validated
    configuration -- not yet the CLI default, see how-to-run.md section
    2.3), 502.5s warm / 591.2s cold mean per 30-camera night vs. C++'s
    648.3s -- Python ~18-23% faster. The still-default --worker-mode
    subprocess path is slower than C++ (~674s).
  - PSF-shape (sigma_y) agreement: mean 0.46%, band-dependent (b=0.78%,
    r=0.45%, z=0.14%) -- consistent with the general pattern that b-band
    correctness trails r/z everywhere it's been measured, because b-band's
    calibration lines are intrinsically fainter/lower-QE, so fewer clear
    the S/N selection threshold and each bundle's fit is less constrained
    -- a property of the input data, not a Python-specific issue.

Current production defaults: --trace-per-fiber-deg 6 (per-fiber trace
basis) with an ndead-gated cross-fiber consensus prior (--trace-prior-deg
1), --footprint-margin 7 (matches C++'s own boundary-fiber window), mixed
float32/float64 precision, grid line search.

===============================================================================
2. STILL OPEN
===============================================================================
- Residual trace-position disagreement: even with every known difference
  accounted for, Python and C++ land on slightly different (both locally
  reasonable) trace solutions on some bundles -- attributed to two
  independently-implemented least-squares solvers converging to different
  local optima, correlated with how far a bundle's trace has drifted from
  its calibration starting guess. Not a discovered bug; every concrete
  candidate mechanism tested has been ruled out. Full detail:
  python-vs-cpp-diff.txt section 1.1.
- A small number of individually-named fibers/bundles with severe local
  data problems (severe ndead, fiber-crossing geometry, or otherwise
  genuinely hard real data) don't fully recover even with the trace-
  consensus prior active -- data-quality floors, not fitting bugs. Named
  cases: python-vs-cpp-diff.txt section 1.3, edge-cases.md.
- Air-vs-vacuum wavelength convention: both pipelines show an identical
  ~0.5A mean offset vs. the line list's reference wavelengths (confirmed:
  a labeling-convention mismatch, not a fitting error -- scoring against
  vacuum-converted references cuts residual scatter ~3.4x). A genuine
  re-fit using vacuum line-list labels is NOT yet safe to ship as-is: the
  input PSF template's own initial guesses are still air-convention, so
  swapping only the line list can start some candidates from a bad initial
  guess and occasionally break either pipeline's numerics outright. Two-
  part fix, neither implemented: (1) rebuild the input PSF template under
  the vacuum convention before switching the line list, (2) add a
  divergence guard so a runaway fit fails gracefully instead of hitting a
  raw allocator/solver crash.
- sigma_y's b-band residual (0.78%) runs noticeably higher than r/z
  (0.14-0.45%) -- leading hypothesis is a weak blue-edge calibration
  signal, not investigated further.
- Two distinct CCD-edge PSF-*shape* effects, tested 2026-09-13, likely two
  distinct causes:
  (a) True-slit-edge (fiber 0/499): real on real data (all 30 cameras,
  Python 1.7-2.4x worse than interior in every band) but does NOT
  reproduce against noiseless arcsim ground truth (Python ratio
  0.41-1.00x, flat/reversed) -- supports a real-data/SNR cause, not a
  Python structural bug. (C++ does show a small residual effect even in
  sim, 1.17-1.44x, unexplained, low priority.)
  (b) Wavelength-domain edges (worse near the edges of each band's own
  coverage, both ends not just red): does NOT disappear in the noiseless
  sim -- if anything stronger and more symmetric there (r-band: 0.20%/
  0.18% at the two edges vs 0.03% mid-band). Survives with zero noise, so
  probably NOT SNR-driven. Tested the leading hypothesis directly
  (raising the wavelength Legendre degree from b/r's default of 1):
  made things ~10-30x *worse* overall, ruling out "just under-
  parametrized," though the U-shape persisted at both degrees. Revised
  hypothesis -- sparse/irregular candidate-line sampling near each
  band's edges, not raw polynomial-domain-edge math -- doesn't cleanly
  explain b-band's own red edge (its worst bin has the *most* catalog
  lines, not the fewest). Genuinely still open. Both small in absolute
  terms, neither a correctness blocker. Full data:
  porting-notes.md, 2026-09-13 (two entries).
- C++'s own fit is not perfectly run-to-run reproducible at the sigma_y
  precision level (~0.1-0.2%): a fresh arcsim C++ refit's fitted GHSIGY
  Legendre coefficients differ meaningfully from the original Aug-28
  reference's, despite near-identical trace positions. Not yet explained
  (candidate cause: thread/BLAS numerics between MPI and the
  single-process workaround used to generate the fresh refit). Blocks a
  clean "is Python closer to truth more often, in aggregate" answer until
  resolved -- Python-vs-truth-directly findings are unaffected.
- Julien Guy's separable-B-spline-PSF proposal was scoped (rough effort
  estimate only) but deliberately not pursued, per Stephen's direction to
  prioritize production-readiness over new modeling work right now.
