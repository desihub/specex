# Reading the Python/JAX port: where to start, and what's actually live

This is the guide Julien Guy asked for -- a way to read `py/specex/` and
trust what's real production code vs. leftover/reference/testing-only code,
without re-deriving it from scratch. It answers two questions: **where do I
start reading**, and **which functions are actually on the path that runs
in production**. For *why* the port's numbers differ from a literal reading
of the paper or the C++ code, see `algorithm-paper-map.md`. For *how* to run
any of this, see `how-to-run.md`. For the full history behind any claim
below, see `porting-notes.md`.

This was generated by a fresh static call-graph analysis of the current
code (2026-09-09) -- an AST walk that indexes every function/method
definition in `specex.py`/`fitter.py`/`psf.py`/`io.py`/`math.py`, follows
every `Name`/`Attribute` reference (not just `Call` nodes -- this codebase
passes bare function references to `Pool.starmap`, so a plain call-site
grep would miss real edges), resolves the module-level `foo_jit = jit(foo)`
wrapping idiom by hand, then walks from the real entry points. It's a
reading aid, not a runtime profiler -- it tells you what calls what
syntactically, not how often or how expensively.

## Where to start

Read in this order:

1. **`specex.py`'s `main()`** (line 923) -- the CLI entry point
   (`python -m specex.specex`). Parses arguments, does GPU/CPU backend
   isolation, and calls `fit_ccd_native()`. Thin; the real work starts one
   level down.
2. **`specex.py`'s `fit_ccd_native()`** (line 634) -- the driver. Spreads a
   camera's 20 bundles across GPUs/workers via a `multiprocessing.Pool`,
   calls `fit_bundle_task()` once per bundle, merges every bundle's result
   into one output PSF via `write_python_psf()`.
3. **`specex.py`'s `fit_bundle_task()`** (line 71) -- one 25-fiber bundle's
   *entire* fit, run as an isolated worker process: reads the preproc image
   (`io.py`), selects spots (`fitter.py`'s `select_bundle_spots_iterative`),
   and runs the joint fit (`fitter.py`'s `PSF_Fitter.fit()`).
4. **`fitter.py`'s `PSF_Fitter.fit()`** (line 1557) -- the actual fit
   engine. This is the one function worth reading slowly: it advances
   through fixed stages (`'flux'` -> `'trace'` -> `'sigma'` -> `'full'`),
   with trace and GHSIGX/GHSIGY frozen once their own stage ends (see
   `CLAUDE.md`'s "Repo layout" section for why this mirrors real C++).
5. **`psf.py`'s `GaussHermitePSF`** -- the shape model `PSF_Fitter.fit()`
   evaluates every iteration. `get_gh_basis()` is the actual speed
   mechanism: a separable 1D `(Bx, By)` decomposition that lets the 2D PSF
   be assembled as an outer-product sum (`O(pixels+params)` instead of
   `O(pixels x params)`) -- this only works because Gauss-Hermite is
   X/Y-separable (see `algorithm-paper-map.md` for why swapping the family
   isn't a config change).
6. **`math.py`** -- shared Legendre/Hermite polynomial bases used by both
   the trace fit and the PSF-shape fit. Small, mostly leaf functions; read
   on demand rather than up front.

**Class relationships**: `PSF_Fitter` wraps one `PSF`; `PSF` holds one
`GaussHermitePSF` (`self.gh_psf`) plus the per-bundle fitted state
(`params_of_bundles`) and per-fiber trace polynomials (`fiber_traces`).
`GaussHermitePSF` itself is stateless (a pure shape-evaluation model) --
everything fitted lives on `PSF`/`PSF_Params`, not on `GaussHermitePSF`.

**There is a second, separate entry point**: `specex.py`'s `run_specex()`
(line 12) wraps the compiled C++ pybind11 extension (`_libspecex`) instead
of the native Python/JAX path above. `desispec`'s real `desi_compute_psf`
entry point calls this directly for every `--backend cpp`/`cpp-direct` run
this project has ever done -- it is real production code for the *C++*
codepath, not a leftover, just not the GPU-native one. (This was briefly
renamed to `run_specex_cpp()` on 2026-09-13 then reverted the same day, to
keep testing against the current, unpatched `../desispec` checkout working
-- see `docs/python-port/desispec-integration-plan.md`; the rename is
still the intended plan for the real desispec integration, just deferred.)
It has its own small subtree in `io.py` (`read_psf`/`write_psf`/
`read_preproc_cpp`/`meta2header`) that `main()` never touches -- don't
expect those four to show up reachable from `main()` below; they're
reachable from
`run_specex()` instead.

## Real code that's *not* on this hot path

Not reachable from `main()`, but not dead either -- three genuinely
different reasons:

- **The C++-wrapper subtree** (`run_specex()`'s own path, see above):
  `read_psf` (`io.py:399`), `write_psf` (`io.py:313`),
  `read_preproc_cpp` (`io.py:456`), `meta2header` (`io.py:10`). Real
  production code for `--backend cpp`/`cpp-direct`, just a different entry
  point than `main()`. (Their docstrings said "LEGACY" until 2026-09-13 --
  written before `CLAUDE.md`'s 2026-09-06 correction that this subtree is
  real production, not a leftover; fixed alongside the same-day rename
  investigation, kept even after the rename itself was reverted.)
- **CI-test-only** (exercised by the real pytest suites `test_math.py`/
  `test_math_psf.py`/`test_vectorization.py`, per `CLAUDE.md`): `GaussHermitePSF.pix_value`
  (`psf.py:205`), `GaussHermitePSF.pix_value_jnp` (`psf.py:172`),
  `Legendre1DPol.derivative` (`math.py:180`),
  `SparseLegendre2DPol.__init__` (`math.py:243`). Correctness-relevant, just
  not called by the production fit path itself.
- **Testing-tool-only**: `get_bundle_spots` (`fitter.py:1304`) -- a
  standalone, non-iterative spot-selection function used by `full_analysis.py`
  and `validate_all_modes.py` (and several one-off scripts now moved to
  `testing/obsolete/`, see `how-to-run.md`), but not by the production
  path, which uses `select_bundle_spots_iterative` instead. Real and
  actively used, just by ad-hoc comparison tooling rather than
  `fit_ccd_native`.

## `testing/run_night.py`: the production orchestration layer on top

Everything above is what runs *inside* one `python -m specex.specex`
process for one camera. `testing/run_night.py` is the layer above it that
actually drives a full 30-camera night in production (`--backend python`,
`cpp`, or `cpp-direct`) -- see `how-to-run.md` section 2.3 for how it
schedules cameras across GPUs/nodes and its `--worker-mode persistent`
optimization. It isn't part of this call graph (it's an orchestrator, not
part of the fitting engine), but it's the thing that actually calls
`main()`'s equivalent (`fit_ccd_native()`, in-process for persistent mode)
per camera.
